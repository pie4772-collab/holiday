# 연차관리 시스템 → 경량 E-HR 전환 로드맵

작성일: 2026-09-30
대상: KBI동양철관 연차관리 시스템 (`pie8405-holiday.mycafe24.ai`)

## 1. 결론

- 경량 E-HR은 **현재 프로젝트를 확장**하는 방식으로 구축한다.
- 급여 계산, 4대보험, 원천세 신고처럼 법적 책임이 크고 매년 규정이 바뀌는 영역은 **기존 급여 프로그램을 유지하고 파일(CSV) 또는 API로 연결**한다.
- 기능 추가에 앞서 **준비작업(2장)**을 먼저 끝낸다. 준비작업은 사용자 화면에 거의 드러나지 않지만, 이후 기능을 안전하게 얹기 위한 기반이다.

### 확장을 선택한 이유

E-HR에서 가장 만들기 번거로운 공통 기반이 이미 갖춰져 있다.

| 기반 | 현재 구현 위치 |
| --- | --- |
| 사원 마스터 (사업장·부서·직급·겸직·입퇴사) | `employees` 테이블, `server/services/employeeService.js` |
| 로그인 (scrypt 비밀번호 해시, 서명 토큰) | `server/services/authService.js` |
| 결재선 (팀장 → 공장장 → 임원 → 대표이사, 결재 좌석) | `server/services/approvalService.js`, `approval_seats` |
| 메일 알림 | `server/services/mailService.js` |
| 감사 이력 (처리 당시 정보 스냅샷) | `leave_approval_logs` |
| 배포 (GitHub → Cafe24) | `docs/AISPACE_DEPLOY.md` |

별도 시스템으로 만들면 사원 정보, 로그인, 결재선을 두 곳에서 동기화해야 한다. 현재 규모(약 80명)에서는 그 부담이 얻는 이점보다 크다.

## 2. 준비작업 (기능 확장 전 필수)

권장 순서대로 정리했다. 1~3번은 반드시 선행하고, 4~6번은 첫 신규 기능과 함께 진행해도 된다.

### 2.1 데이터베이스 교체 — 최우선

**현재 상태**
- `sql.js`(WebAssembly SQLite)가 DB 전체를 메모리에 올리고, 저장할 때마다 파일 전체를 다시 쓴다 (`server/db.js`의 `persist()`).
- 연차 데이터 규모에서는 문제가 없지만, 근태 기록이나 결재 문서가 쌓이면 저장 속도가 떨어진다. 저장 도중 서버가 멈추면 파일이 손상될 위험도 있다.

**작업 내용**
- 선택지 A: `better-sqlite3`(파일 기반 SQLite, 변경분만 기록) — 코드 변경이 가장 적다.
- 선택지 B: Cafe24 MySQL — 동시 사용자와 데이터가 크게 늘어날 경우.
- 권장: **A로 먼저 전환**하고, 필요해지면 B로 옮긴다. 현재 `getDb().prepare().run/get/all` 형태의 래퍼를 유지하면 서비스 코드는 거의 바꾸지 않아도 된다.
- 마이그레이션 방식 정비: 지금은 `db.js` 안에서 `ALTER TABLE`과 `app_meta` 키로 처리하고 있다. 이를 번호가 붙은 마이그레이션 파일(`database/migrations/001_*.sql`)로 분리한다.

**완료 기준**
- 기존 데이터(사원, 연차 발생·사용, 승인 이력, 정산)를 이전하고 건수·잔여일수가 일치하는지 검증한다.
- Cafe24 컨테이너가 재시작되어도 `/app/user_data`의 DB가 유지되는지 확인한다.

**진행 결과 (2026-09-30)**
- 선택지 A의 `better-sqlite3`는 Cafe24 리눅스에서 네이티브 빌드가 실패해 `sql.js`로 바꿨던 이력이 있다(커밋 `c96ff82`). 그래서 **Node 내장 SQLite(`node:sqlite`)**로 전환했다. 네이티브 빌드가 필요 없고, 변경분만 파일에 기록한다.
- `node:sqlite`가 없는 환경(Node 22.13 미만)에서는 `sql.js`로 자동 전환한다. 이때도 임시 파일에 쓴 뒤 교체하는 방식으로 저장해, 저장 중 중단돼도 원본 파일이 손상되지 않는다. 환경변수 `DB_DRIVER=sqljs`로 강제 지정할 수 있다.
- DB 파일 형식은 그대로라 데이터 변환이 필요 없다. 새 드라이버로 처음 열 때 원본을 `holiday.db.pre-node-sqlite.bak`으로 한 번 자동 보관한다.
- `db.transaction(fn)`을 추가했다. 서버 시작 시 스키마 보정(`migrate()`)을 하나의 트랜잭션으로 묶었다.
- 번호형 마이그레이션 도입: `database/migrations/NNN_설명.sql`을 순서대로 한 번씩 적용하고 `schema_migrations` 테이블에 기록한다. 기존 `migrate()`는 기준선(`001_baseline.sql`)으로 두고, 이후 변경부터 파일로 추가한다.
- `/health` 응답에 `dbDriver`, `node` 버전을 표시한다.
- 로컬 검증 (Node 24):
  - 기존 16개 테이블의 행 수와 내용 해시가 전환 전과 일치 (`scripts/db-fingerprint.mjs`)
  - 결재선 검증 스크립트 3종의 출력이 전환 전과 동일 (두 드라이버 모두)
  - 사원 등록, 연차 발생 추가·수정·삭제, 연차 사용 등록 후 서버 강제 종료·재시작에도 데이터 유지
  - 같은 쓰기 작업 후 모든 컬럼의 저장 타입이 `sql.js`와 동일 (정수를 REAL로 저장하는 차이는 BigInt 바인딩으로 해결)
  - 트랜잭션 롤백·커밋 정상
- 운영 서버 확인 결과: Cafe24 런타임이 Node 20으로 고정되어 있어 `node:sqlite` 대신 `sql.js`(안전 저장 방식)로 동작한다.

**PostgreSQL 전환 (2026-09-30, 운영 적용 완료)**
- 운영 서버가 Node 20 고정이라 파일 DB의 한계가 남아 있고, E-HR로 확장하면 동시 사용과 데이터가 늘어나므로 Cafe24가 지원하는 **PostgreSQL**을 운영 DB로 쓰도록 준비했다.
- 모든 DB 호출을 비동기(`await`)로 바꿨다. 서비스 코드는 계속 `getDb().prepare(sql).get/all/run` 형태를 쓰고, DB 종류별 차이는 `server/db.js`가 흡수한다.
  - SQLite: 기존 드라이버 그대로. 트랜잭션 중에는 다른 요청의 쿼리가 끝날 때까지 기다린다.
  - PostgreSQL(`server/dbPostgres.js`): 연결 풀 사용. `?` 자리표시자, `datetime('now','localtime')`, NULL 정렬 순서(SQLite는 NULL이 가장 작음), 대소문자 섞인 별칭, INSERT 후 새 id(`RETURNING id`)를 자동으로 맞춰 준다.
- 선택 방법: 환경변수 `APP_DB_CLIENT=postgres`(로컬은 `DB_CLIENT`도 가능, Cafe24는 콘솔의 `DB_*` 변수를 전달하지 않음). 접속 정보는 Cafe24가 자동 주입하는 `DB_HOST`·`DB_PORT`·`DB_NAME`·`DB_USER`·`DB_PASSWORD`(또는 `DATABASE_URL`)를 쓴다. `DB_CLIENT`를 지우면 즉시 SQLite로 돌아간다.
- 스키마: `database/postgres/schema.sql`. 날짜는 SQLite와 같은 문자열 형식, 문자열 정렬은 SQLite와 같은 바이트 순서(`COLLATE "C"`)로 저장한다. 서버 시작 때마다 `IF NOT EXISTS`로 적용한다.
- 자동 데이터 이전(`server/dbImport.js`): PostgreSQL이 비어 있으면 서버 시작 시 SQLite 파일(`/app/user_data/holiday.db`)의 모든 표를 한 트랜잭션으로 옮기고, 표마다 행 수와 내용 해시를 대조한 뒤에만 커밋한다. 하나라도 다르면 전부 취소되어 PostgreSQL은 빈 채로 남는다. SQLite 파일은 건드리지 않는다. 이전 기록은 `app_meta.sqlite_import`에 남는다.
- 동시성: 같은 직원의 연차 신청, 같은 신청건의 결재는 PostgreSQL에서 한 번에 하나씩 처리되도록 잠금을 건다.
- 번호형 마이그레이션은 두 DB에 공통으로 쓰고, 문법이 다르면 `NNN_설명.sqlite.sql` / `NNN_설명.postgres.sql`로 나눈다.
- 로컬 검증 (PostgreSQL 18, Node 24):
  - API 스냅샷 825단계(조회 전체 + 사원·연차·결재·정산 쓰기 흐름)가 SQLite(`node:sqlite`, `sql.js`)와 PostgreSQL에서 모두 전환 전 기준값과 100% 일치 (`scripts/run-api-snapshot.ps1`, `scripts/api-snapshot.mjs --compare`)
  - 한국어 정렬(ko-KR ICU)로 만든 PostgreSQL DB에서도 동일
  - 이전 후 데이터 표의 행 수·내용 해시가 SQLite와 동일 (`scripts/db-fingerprint.mjs`), 결재선 검증 스크립트 출력 동일
  - 재시작 시 다시 이전하지 않음, 재시작 후 데이터 유지, 동일 신청 6건 동시 요청 시 1건만 접수
  - 저장 시각이 Node 프로세스의 현지 시각과 같은 형식·시간대로 기록됨 (서버 시간대를 UTC·뉴욕으로 바꿔도 일치)
  - 부모 없는 행은 삭제 규칙대로 정리(CASCADE는 제외, SET NULL은 비움)하고 로그로 남김. 변환할 수 없는 값이 있으면 이전 전체가 취소됨
- 운영 적용 절차는 `docs/AISPACE_DEPLOY.md`의 "PostgreSQL 전환" 참고.
- 운영 적용 결과 (2026-09-30): Cafe24 PostgreSQL로 전환 완료. 직원 80명·사용자 80명 이전, 재시작 후에도 유지 확인. Cafe24는 콘솔에서 넣은 `DB_*` 이름의 환경변수를 앱에 넘기지 않아 `APP_DB_CLIENT`로 지정한다.

### 2.2 역할 기반 권한 (RBAC) — 적용

> **결정 (2026-09-30)**: 처음에는 관리자 권한 하나로 통일하기로 했다가, 같은 날 아래 역할 범위를 추가하기로 바꿨다. **연차 결재 라인 방식은 그대로 유지**한다.

**이전 상태**
- 권한이 `employees.is_admin` 하나(관리자/일반)뿐이었고, `requireAdmin` 미들웨어가 모든 관리 기능을 한꺼번에 허용했다.

**작업 내용**
- 역할 테이블 추가: `employee_roles` (사원 1명이 여러 역할을 가질 수 있음)
- 기본 역할안

  | 역할 | 범위 |
  | --- | --- |
  | 시스템관리자 | 전체 설정, 권한 부여 |
  | 인사담당 | 전 사업장 인사기록·연차·결재 이력 |
  | 급여담당 | 통상임금, 정산, 부채 (민감정보 열람) |
  | 사업장관리자 | 소속 사업장 사원만 |
  | 부서장 | 소속 부서원 조회, 결재 |
  | 일반 | 본인 정보만 |

- 미들웨어를 `requirePermission('leave.view')`처럼 권한 단위로 바꾸고, 사업장·부서 범위 필터를 공통으로 둔다.

**진행 결과 (2026-09-30)**
- 스키마: `database/migrations/003_employee_roles.*.sql`. 기존 `is_admin = 1` 사용자 6명(이재용·박지은·이규형·김춘태·김남은·최윤경)은 모두 **시스템관리자**로 옮겼다.
- 역할별 메뉴·권한 (`server/services/accessService.js`)

  | 역할 | 지정 방식 | 볼 수 있는 관리 메뉴 |
  | --- | --- | --- |
  | 시스템관리자 | 사원 명부 "역할" | 전체 + 역할 지정 + 메일 서버 |
  | 인사담당 | 사원 명부 "역할" | 연차 관리·승인 이력·사원 명부(수정)·결재 라인·연차 보고서(확정) |
  | 급여담당 | 사원 명부 "역할" | IFRS 연차부채·연차 정산·통상임금, 사원 명부·연차 보고서 조회 |
  | 사업장관리자 | 사원 명부 "역할" | **본인 사업장만**: 연차 관리(조회·수정)·승인 이력·사원 명부 조회·연차 보고서 조회 |
  | 부서장 | 자동 (직급 또는 겸직직급이 팀장) | 직원 화면 "부서원 연차"에서 결재 대상 부서원의 연차 현황·내역 조회 |
  | 일반 | 기본 | 본인 정보만 |

- **연차 결재는 바뀌지 않는다**: 결재 로직은 계속 `employees.is_admin`을 보고, 역할을 저장할 때 `is_admin`을 "시스템관리자 또는 인사담당"과 맞춘다. 그래서 두 역할은 기존 관리자처럼 모든 단계 승인·사업장 관리자 메일 대상이 되고, 결재 좌석·부서장 결재선은 그대로다. 부서장 판정도 결재선과 같은 함수(`isTeamLeaderFor`)를 쓴다.
- 서버가 모든 관리 API에서 권한과 사업장 범위를 확인한다. 사업장관리자는 다른 사업장 직원을 조회·수정할 수 없고, 목록·통계·보고서·승인 이력도 본인 사업장만 받는다.
- 전에는 로그인 없이도 열리던 `/employees/:id/leave/history`, `/leave/usages`를 본인·권한 범위 안 관리자·담당 부서장만 볼 수 있게 막았다.
- 시스템관리자는 최소 1명 남아야 하고, 사업장이 없는 직원은 사업장관리자로 지정할 수 없다. 직원 등록·수정 화면의 "관리자 권한" 체크는 없앴다(역할 지정으로 대체).
- 검증 (로컬, SQLite·PostgreSQL 모두):
  - 역할별 권한 시나리오 54개 통과 (사업장 범위, 403 차단, 부서장 조회, `is_admin` 동기화 등)
  - 운영과 같은 상태(PostgreSQL에 데이터가 있고 003 미적용)에서 마이그레이션하면 시스템관리자 6명이 매핑됨
  - API 스냅샷 825단계에서 새로 추가된 항목(`roles`, `permissions` 등)을 빼면 기준값과 완전히 같음 → 연차 신청·결재 결과 변화 없음

### 2.3 보안 기본기 정비

현재 코드에서 확인한 보완 필요 사항이다.

| 항목 | 현재 | 조치 |
| --- | --- | --- |
| 세션 서명 키 | `SESSION_SECRET` 미설정 시 코드에 적힌 기본값 사용 | 운영 환경에서 필수 환경변수로 강제하고, 없으면 서버 시작 실패 |
| 초기 비밀번호 | 전 직원 `123456` | 첫 로그인 시 비밀번호 변경 강제, 최소 길이 정책 |
| 로그아웃·강제 만료 | 토큰이 서버에 저장되지 않아 발급 후 무효화 불가 | 세션 테이블 또는 토큰 버전 컬럼으로 퇴사자·비밀번호 변경 시 즉시 만료 |
| 메일 계정 비밀번호 | `mail_settings.password` 평문 저장 | 암호화 저장 (2.4의 암호화 키 사용) |
| 로그인 시도 제한 | 없음 | 연속 실패 시 일시 잠금 |

**진행 결과 (2026-09-30)**
- **세션 서명 키**: 코드에 적힌 기본값을 없앴다. `SESSION_SECRET`(32자 이상)이 있으면 그 값을, 없으면 비밀 키 파일에서 파생한 값을 쓴다. 필수 환경변수로 강제하는 대신 키 파일 방식을 택한 이유는 Cafe24 콘솔 환경변수가 재배포 방식에 따라 전달되지 않는 경우가 있어, 설정 누락으로 운영 서버가 멈추는 위험을 피하기 위해서다.
  - 비밀 키 파일: 운영 `/app/user_data/secret.key`(재배포해도 유지, 프로젝트 백업에 포함), 로컬 `database/secret.key`. 처음 시작할 때 자동 생성하고 Git에는 올리지 않는다. `APP_SECRET_KEY`(16진수 64자)로 직접 지정할 수도 있다.
- **초기 비밀번호 변경 강제**: 초기 비밀번호(`123456`)로 로그인하면 비밀번호 변경 화면으로 보내고, 변경 전에는 서버가 다른 API를 모두 거부한다(`403 PASSWORD_CHANGE_REQUIRED`).
  - 정책: 8자 이상, 영문+숫자 포함, 초기 비밀번호·사번 포함 금지, 현재 비밀번호와 달라야 함.
  - 사이드바의 "비밀번호 변경"에서 언제든 바꿀 수 있다.
- **세션 강제 만료**: `users.token_version`을 토큰에 넣고 요청마다 DB와 대조한다. 비밀번호 변경·관리자 초기화·로그아웃 시 그 사용자의 기존 토큰이 모두 무효가 된다. 퇴사 처리된 직원의 토큰도 즉시 거부한다.
- **메일 계정 비밀번호 암호화**: `mail_settings.password`를 AES-256-GCM(`enc:v1:` 접두어)으로 저장한다. 서버 시작 시 평문으로 남아 있던 값을 자동으로 암호화한다. 비밀 키 파일을 잃으면 복호화할 수 없으므로 메일 설정에서 비밀번호를 다시 입력하면 된다(서버는 정상 동작).
- **로그인 시도 제한**: 5회 연속 실패하면 15분간 잠근다. 로그인 성공 시 실패 횟수를 초기화한다.
- **관리자 비밀번호 초기화**: 사원 명부의 "비번 초기화"로 초기 비밀번호로 되돌린다. 잠금 해제·기존 세션 종료가 함께 되고, 다음 로그인 때 변경을 요구한다.
- 스키마: `database/migrations/002_auth_security.sql` (`users`에 `token_version`, `failed_login_count`, `locked_until`, `password_changed_at` 추가).
- 검증 (로컬, SQLite·PostgreSQL 모두):
  - 보안 시나리오 24개 통과: 변경 강제·정책·이전 토큰 무효·잠금·초기화·로그아웃·위조 토큰 등
  - API 스냅샷 825단계에서 기준값과의 차이는 `/auth/me`에 추가된 `mustChangePassword` 항목 2건뿐이고, SQLite와 PostgreSQL 결과는 완전히 같음
  - 평문 메일 비밀번호 자동 암호화, 암호화된 값으로 SMTP 인증까지 진행되는 것 확인

### 2.4 민감정보 보호 (개인정보보호법 대응)

주민등록번호, 계좌, 연봉, 가족정보를 다루기 전에 반드시 갖춘다.

- **암호화 저장**: 민감 컬럼은 AES-256-GCM으로 암호화하고, 키는 환경변수로 관리한다(DB와 분리).
- **화면 마스킹**: 기본은 `900101-1******` 형태로 보여주고, 권한자가 "보기"를 눌렀을 때만 원문을 표시한다.
- **열람 기록**: 누가, 언제, 누구의 어떤 항목을 열람·다운로드했는지 `privacy_access_logs`에 남긴다.
- **최소 수집**: 법정 필요 항목만 수집하고, 퇴사자 정보의 보관 기간과 파기 절차를 정한다.

### 2.5 파일 저장소와 백업

- **첨부파일 저장**: 증빙, 계약서, 증명서 PDF를 둘 곳이 필요하다. `/app/user_data/files/` 아래 저장하고 DB에는 메타정보(원본명, 크기, 해시, 업로더)만 둔다. 다운로드는 권한 확인 API를 거치게 한다.
- **정기 백업**: DB와 첨부파일을 매일 백업하고 최소 30일 보관한다. 복구 절차를 문서화하고 분기마다 복구 테스트를 한다.

### 2.6 코드 구조 모듈화

- `server/services/leaveService.js`가 약 2,000줄이다. 다음처럼 나눈다.
  - `server/modules/leave/` (발생·사용·정산·부채·보고서)
  - `server/modules/approval/` (범용 결재 엔진, 3.2와 연계)
  - `server/modules/hr/` (사원·인사기록·발령)

## 3. 확장 기능 (추천 순서)

기존 기반을 얼마나 재사용할 수 있는지, 업무 효과가 얼마나 큰지를 기준으로 순서를 정했다.

### 3.1 인사기록카드

- **내용**: 기본정보, 학력, 경력, 자격·면허, 가족, 병역, 발령 이력, 교육 이력
- **재사용**: `employees` 테이블을 확장하고, 사원 명부 화면에 상세 탭을 추가한다.
- **선행 조건**: 2.4 민감정보 보호, 2.2 권한
- **효과**: 흩어진 엑셀 인사대장을 한 곳으로 모은다. 이후 모든 기능의 기준 데이터가 된다.

**진행 결과 (2026-09-30)**
- **범위 결정**: 주민등록번호·계좌·연봉과 가족 정보는 저장하지 않는다(급여 프로그램에만 둔다). 그래서 2.4의 암호화·마스킹·열람 기록 없이 진행했고, 나중에 민감정보를 넣게 되면 2.4를 먼저 한다.
- **항목**: 기본정보(생년월일·성별·휴대전화·개인 이메일·주소·비상연락처), 병역, 학력, 경력, 자격·면허, 발령 이력, 교육 이력, 평가 결과
  - 발령 이력은 기록만 한다. 발령일에 사원 정보를 자동으로 바꾸는 기능은 3.5에서 한다.
- **스키마**: `database/migrations/004_personnel_records.*.sql`
  - `employee_profiles`: 기본정보·병역, 직원 1명당 1행
  - `employee_records`: 학력·경력·자격·발령·교육·평가 이력, 구분(`category`)별 여러 행
  - 항목 정의는 `src/constants/personnel.js` 한 곳에서 서버와 화면이 같이 쓴다.
- **권한**

  | 역할 | 인사기록카드 |
  | --- | --- |
  | 시스템관리자·인사담당 | 전체 조회·수정, CSV 내려받기·올리기 |
  | 사업장관리자 | 본인 사업장 직원 조회만 |
  | 직원 | "내 인사기록"에서 본인 카드 조회만 (평가 결과는 보이지 않음) |

- **화면**: 관리 메뉴 "인사기록카드"(목록 → 직원별 카드, 탭으로 항목 구분), 직원 메뉴 "내 인사기록"
- **엑셀 인사대장 일괄 등록 (CSV)**
  - 내려받은 파일이 곧 양식이다. 기본정보·병역 파일과 이력 파일 두 가지로 나뉜다.
  - 기본정보는 사번 기준으로 덮어쓴다. 이력은 ID가 있는 행은 고치고, ID가 없는 행은 추가하며, 똑같은 이력은 건너뛴다.
  - 한 줄이라도 오류(없는 사번, 날짜 형식, 선택지 밖 값 등)가 있으면 아무것도 반영하지 않고 오류 행 번호를 알려 준다.
  - 날짜는 `2024-03-02`, `2024.3.2`, `20240302` 모두 받고, 이력은 연월(`2024-03`)만 써도 된다.
- **함께 고친 것**
  - PostgreSQL에서 마이그레이션으로 새로 만든 테이블에 행을 추가할 때 새 `id`를 돌려받지 못하던 문제를 고쳤다. 마이그레이션 후 테이블 목록을 다시 읽는다.
  - 요청 본문 한도를 2MB로 늘렸다(CSV 업로드용).
- **검증** (로컬, SQLite·PostgreSQL 모두)
  - 인사기록카드 시나리오 38개 통과: 저장·날짜 정리·검증 오류, CSV 왕복·중복 건너뜀·ID 수정·오류 시 전체 미반영, 역할별 권한, 본인 화면의 평가 숨김
  - 운영과 같은 상태(PostgreSQL에 데이터가 있고 004 미적용)에서 마이그레이션과 이력 추가가 정상 동작
  - API 스냅샷 825단계는 기존 결과와 같다(역할 항목 제외).

### 3.2 범용 전자결재

- **내용**: 연차 결재 구조를 일반화해서 여러 신청서를 처리한다.
  - 출장·외근 신청, 경조금 신청, 휴직·복직, 증명서 발급 신청, 교육 신청
- **재사용**: `approvalService.getApprovalChain`, 결재 좌석, 메일 알림, 승인·반려 이력 화면을 그대로 확장한다.
- **설계 요점**:
  - `approval_documents`(문서 유형, 신청자, 상태, 본문 JSON)와 `approval_steps`(단계별 결재자, 처리 결과) 테이블
  - 문서 유형마다 입력 양식과 결재선 규칙을 설정으로 정의
  - 기존 연차 신청은 문서 유형 중 하나로 흡수 (데이터 이전 포함)
- **효과**: 종이·메일로 오가던 결재가 한 곳에 모이고, 근로감독 대비 이력이 모든 신청서로 넓어진다.

### 3.3 증명서 발급

- **내용**: 재직증명서, 경력증명서, 퇴직증명서 PDF 발급
- **재사용**: 인사기록카드 데이터, 전자결재(발급 신청 → 승인 → 발급)
- **설계 요점**: 발급번호와 발급대장 보관, 회사 직인 이미지 삽입, 진위 확인용 발급번호 조회
- **효과**: 인사담당자의 반복 업무를 크게 줄인다.

### 3.4 근태 관리

- **내용**: 출퇴근 기록, 초과·야간·휴일근무 신청과 승인, 월 근태 마감
- **재사용**: 전자결재(초과근무 신청), 연차 사용 내역(휴가일 자동 반영), 공휴일 계산(`korean-lunar-calendar`)
- **설계 요점**:
  - 지문·출입 단말기가 있으면 그 기록을 CSV나 API로 가져온다 (단말기를 대체하지 않음)
  - 주 52시간 초과 경고
  - 월 마감 결과를 급여 프로그램으로 내보내는 CSV
- **효과**: 근로시간 관리 의무 대응, 급여 계산 입력 자료 자동화

### 3.5 조직도·발령 관리

- **내용**: 부서 계층 구조, 조직도 화면, 인사 발령(부서 이동·승진·겸직) 등록과 이력
- **재사용**: 부서·사업장 코드, 결재 좌석 범위(`approval_seat_scopes`)
- **효과**: 발령일에 맞춰 사원 정보와 결재선이 자동으로 바뀐다. 조직 개편 때 수작업이 줄어든다.

### 3.6 공지사항·사내 게시판

- **내용**: 전사·사업장별 공지, 필독 확인 여부, 첨부파일
- **재사용**: 권한(사업장 범위), 메일 알림, 파일 저장소
- **효과**: 규정 변경, 연차 촉진 통지 같은 공지를 전달하고 확인한 기록을 남긴다.

### 3.7 (선택) 평가·교육 관리

- **내용**: 법정의무교육 이수 관리, 간단한 목표·평가 기록
- 필요성이 확인된 뒤 착수한다.
